## 为什么这样设计

### 问题 1：浏览器沙箱无法写文件

浏览器自动化工具（如 Playwright/Puppeteer 的 evaluate 上下文）通常不提供文件系统访问。

**解法**：本地 HTTP 服务 + 页面 fetch。

```
page.evaluate → fetch(127.0.0.1:18765/collect) → Python HTTPServer → 写文件
```

**为什么可行**：Chrome 把 loopback 地址（127.0.0.1）视为可信来源，不受混合内容策略限制。

**为什么不用 WebSocket**：HTTP 更简单，无连接管理负担，且 Python 标准库自带 HTTPServer。

### 问题 2：判定需要可复现、可审计

如果用 LLM 判定每一条 JD：
- 不可复现（同一条 JD 两次判定可能不同）
- 不可审计（无法解释为什么拒）
- 有成本（每条都要 token）
- 慢（每次几百毫秒到几秒）

**解法**：确定性规则引擎。规则是硬编码的词表和正则，输入相同必然输出相同。

**LLM 只用于**：规则无法覆盖的模糊判断（如「这个 JD 的技能栈是否超出我的能力范围」），且是**批量离线**跑，不在主链路上。

### 问题 3：采集会被推荐广告污染

招聘网站搜索列表里会插入「为你推荐」的广告卡，与搜索词无关。

**解法**：标题必须包含当前关键词才采集。

```javascript
if (cardTitle(card).indexOf(keyword) < 0) continue;
```

**效果**：某次采集中，4981 张卡片只有 717 张是真命中（14%），过滤掉 85% 的噪声。

### 问题 4：JD 的行业标签误杀岗位

JD 开头常有公司行业标签（如「化工/制药/医疗」），如果全文本匹配否决词，会把「化工公司招 IT 运维」误杀。

**解法**：按「岗位职责/任职要求」等标记把 JD 切成「标签区」和「正文区」，否决词只查正文区。

```python
tags, body = split_jd(jd)
# 强专业词只查 body，不查 tags
```

### 问题 5：会话列表实时重排

聊天页的会话列表会因新消息而重排，固定坐标点击必然点错。

**解法**：三重校验。

1. 点击前：实时扫描列表，姓名 + 公司双匹配定位
2. 点击时：用 CDP `Input.dispatchMouseEvent`（合成 click 无效）
3. 点击后：验证右侧窗口是否显示目标公司，失败重试

### 问题 6：工具调用超时

浏览器自动化工具通常有硬超时（如 120 秒），长任务会被中断。

**解法**：分段执行。

- 每段预算 95 秒
- 每 5 条上报一次
- 段间休息 20-25 秒（同时防风控）

## 数据流详解

### 采集阶段

```
1. 注入驻留脚本到搜索页
2. __startCollector({keywords, cityCode}) 启动
3. 循环每个关键词：
   a. 切换关键词（输入框 + Enter，不刷新页面）
   b. 滚动到底部加载全部卡片
   c. 逐卡点击 → 读详情面板 → 过滤非关键词命中
   d. 每 5 条 fetch 到 collect_server
4. collect_server 去重后追加到 index.jsonl
```

### 判定阶段

```
1. 读 index.jsonl（逐行）
2. 跳过无 JD 的记录
3. judge() 按规则优先级判定
4. 追加到 verdicts.jsonl
5. 支持增量（跳过已判）和全量（--reset）
```

### 投递阶段

```
1. GET /apply/queue（服务端实时计算：判投 - 已投 - 无URL）
2. 逐条：
   a. 打开职位页
   b. 双重校验（标题+公司）
   c. 检测验证码/登录失效
   d. 点击投递
   e. 确认弹窗
3. POST /apply/result 批量落盘
```

### 消息处理阶段

```
1. 扫描会话列表（含未读数）
2. 按未读排序，从上往下处理
3. 每个会话：
   a. 三重校验定位
   b. 读取聊天记录 + 岗位卡片
   c. 判断意图（要简历 / 已介绍 / 已拒绝）
   d. 执行动作（同意简历 / 追问 / 婉拒）
4. 记录到消息台账
```

## 扩展性设计

### 增加新平台

1. 实现新的采集器（页面内脚本）
2. 复用 `collect_server`（数据格式统一）
3. 复用 `judge_engine`（规则与平台无关）
4. 实现新的投递驱动

### 增加新规则

在 `judge_engine.py` 中：
1. 添加词表常量
2. 在 `judge()` 中插入规则（注意优先级）
3. 回扫历史数据翻转已判记录

### 增加新数据维度

在采集时增加字段，`collect_server` 无需修改（透传 JSON）。

## 性能数据

| 阶段 | 吞吐 | 说明 |
|---|---|---|
| 采集 | ~1.5 条/秒 | 受限于页面渲染和点击间隔 |
| 判定 | ~5000 条/秒 | 纯 CPU 正则匹配 |
| 投递 | ~0.15 条/秒 | 受限于页面加载和风控 |
| 看板生成 | ~1 秒 | 读全量数据 + 渲染 HTML |
